# AGENTS.md

Guidance for AI agents (and humans) working in this repo. Read this before making changes — it captures conventions that aren't obvious from the code alone.

## What this is

React frontend for SolarOS, replacing the old vanilla-JS site at the sibling repo `../solaros-online`. Talks to the FastAPI backend at `../solaros-online-backend` — that repo's `ApiSpecs.md`/`DbSchema.md` are the nominal API contract, but **the backend's live `http://127.0.0.1:8000/openapi.json` is the actual source of truth** when the two disagree. This has happened more than once: `ApiSpecs.md` called the agreement public-accept endpoint "deferred," but it's implemented and working; several Quote fields (`price_per_watt`, `gst_rate`, `daily_yield`, etc.) were added to the live schema after a gap-analysis conversation without the prose being updated everywhere. Before building against an endpoint, check `openapi.json`'s `components.schemas` for the real field names/types/required-ness, not just the markdown doc.

Old repo (`../solaros-online`) is a vanilla HTML/JS/CSS static site with no build step, migrated from feature-by-feature. When porting a feature, its business logic (calculations, regex extraction, field names) is usually worth reading first — see "Ported logic" below.

## Stack

React 19 · TypeScript · Vite · react-router-dom · **no state management library, no UI component library, no CSS framework**. Styling is hand-written CSS per page/feature, using CSS custom-property tokens from `src/styles/tokens.css` (colors, radius, shadow, font). No test suite exists — verification is `npx tsc -b` (typecheck) plus manually driving the app against the real local backend (see "Verification convention" below).

## Layout

```
src/api/              one file per backend domain (leads.ts, quotes.ts, amcPlans.ts, ...) —
                       thin wrappers around apiRequest(), typed request/response shapes
src/lib/               cross-cutting: AuthContext, ProtectedRoute, RequireSystemAdmin,
                       roles.ts, AppLayout (sidebar/topbar shell), and two ported
                       calculation engines (quoteCalculations.ts, billExtractor.ts)
src/pages/<domain>/   one folder per feature area, each with its own page component(s)
                       and a co-located .css file (e.g. pages/quotes/QuoteBuilderPage.tsx
                       + QuoteBuilderPage.css)
src/styles/tokens.css  shared design tokens, imported once in main.tsx
src/App.tsx            all routing — public routes, /login|/register|/activate,
                       /app/* behind ProtectedRoute, /app/admin/* additionally behind
                       RequireSystemAdmin
```

`src/pages/teams/` exists as an empty directory from the initial scaffold — Phase 10 hasn't been built yet, don't assume anything lives there. `src/pages/projects/` now holds Phase 8 (`ProjectsPage`, `ProjectDetailPage`).

## Conventions to follow

**API client pattern.** Every backend domain gets one `src/api/<domain>.ts` file: typed request/response interfaces plus thin functions calling `apiRequest<T>(path, opts)` from `src/api/client.ts`. `apiRequest` handles the `Authorization: Bearer` header, JSON (or `FormData` for file uploads — see `uploadBrandingLogo`/logo upload), and throws `ApiError` (with `.status`/`.code`/`.message`) on any `{"error": {...}}` response — catch `ApiError` specifically in UI code, don't parse `.message` blindly since `.code` is more stable. Don't call `fetch` directly from a page component.

**Decimal fields come back as strings.** Backend Decimal columns (`total_amount`, `subsidy_amount`, `rate_per_kw`, etc.) serialize as JSON strings, not numbers, to avoid float precision loss. Wrap with `Number(...)` before doing math; the TS types in `src/api/*.ts` already mark these as `string | null` to make this explicit at the type level — don't "fix" the type to `number`.

**Auth is a bearer token in `localStorage`**, not cookies. `src/api/client.ts` holds it in a module-level variable synced to `localStorage`; `AuthContext` (`src/lib/AuthContext.tsx`) restores the session on page load via `GET /me` if a token exists, so a reload doesn't lose login state. Role-based landing/redirects live in `src/pages/HomeRedirect.tsx` and `src/lib/roles.ts` (`isSystemAdmin`) — system admins land on `/app/admin/entities`, entity users on `/app/leads`.

**The "add one line at a time" list editor is the standard pattern for any string-array field** editable by the user — AMC plan inclusions, entity Documents tab (quote_notes/agreement_notes/custom_terms_and_conditions), Quote/Agreement terms. One text input + an "+ Add" button (Enter key also works), existing entries render as removable chips below. This replaced an earlier newline-split-textarea approach that the user explicitly asked to change — don't reintroduce a textarea for a string-array field; copy the pattern from e.g. `src/pages/amc/AmcPlanForm.tsx` or `src/pages/entity/tabs/DocumentsTab.tsx`.

**Quote and Agreement share one calculation engine and one visual language, deliberately.** `src/lib/quoteCalculations.ts`'s `computeQuote()` is a pure port of the old repo's `quote-render.js` `compute()` — base cost, GST, subsidy (explicit amount or the residential-only PM Surya Ghar ladder via the exported `subsidyForKw()`), net investment, generation/savings/payback, 25-year lifetime savings, CO2/tree impact, payment milestones. **Agreement has no pricing/system fields of its own** (confirmed via the live `AgreementResponse` schema — just `terms`/`amc_id`/`amc_duration_years`/`status`/`signed_at`), so `AgreementBuilderPage` always computes from the lead's linked Quote, shown as a read-only "From quote" block, and reuses `QuoteBuilderPage.css` directly (`import "../quotes/QuoteBuilderPage.css"`) rather than duplicating the preview-panel styles. If Quote's calc logic changes, Agreement's preview changes with it for free — that's intentional, keep it that way.

**Entity document-customization defaults fold into the editable list, they don't stay separate.** `document_customization.custom_terms_and_conditions` + `quote_notes` (or `agreement_notes` for agreements) are merged into one `terms` array when a new Quote/Agreement is created — not kept as a separate free-text "Notes" field the admin has to reconcile. Each merged line is individually addable/removable via the same list editor. See the `terms:` construction in `QuoteBuilderPage`'s/`AgreementBuilderPage`'s load effect.

**Locked-state fields, not locked-state pages.** Once a Quote/Agreement's status leaves the editable state (`GENERATED`/`NEW`), don't hide the form — disable every input (`disabled={locked}`) and hide the remove/add controls, so the admin can still see exactly what was agreed. Matches the backend's `QUOTE_LOCKED`/`AGREEMENT_LOCKED` errors, which fire on write attempts past that point.

**Share links load eagerly, never behind a manual button.** `POST .../share` (quotes and agreements) is idempotent — same URL on every call once one exists, per `ApiSpecs.md`. Fetch it in a `useEffect` keyed on the quote/agreement id as soon as one exists, rather than requiring a "Get share link" click. (Quote's token *does* get replaced if the original is consumed by an accept action — that's expected, not a bug, since a consumed token can't be reused; Agreement's stays stable even after acceptance.)

**Auto-filled defaults must land in the actual input, not just the live preview.** If a value has a computed fallback (e.g. suggested subsidy amount, AMC duration defaulting to 1 year on plan selection), pre-populate the form field itself — don't rely on the preview alone to show what "will" be used. Track whether the admin has manually overridden a computed default with a `*Touched` boolean state (see `subsidyTouched` in `QuoteBuilderPage`) so autocompute doesn't clobber a real edit.

**Role-based route trees, not role-based components.** System-admin-only pages live under `/app/admin/*` behind `<RequireSystemAdmin />` in `App.tsx`; everything else behind `<ProtectedRoute />` alone. Sidebar links in `AppLayout.tsx` are conditionally rendered on `systemAdmin`/`user?.entity_id`, mirroring the route guards — keep both in sync when adding a page.

**Ported logic gets a comment explaining the port, not a rewrite from scratch.** `quoteCalculations.ts` and `billExtractor.ts` (electricity-bill PDF extraction, using `pdfjs-dist` as a real npm dependency instead of the old repo's CDN script) are line-for-line ports of working regex/math from the old repo, with the old repo's dead code (an unreachable Tesseract OCR fallback) deliberately dropped rather than carried forward. When porting another old-repo feature, check whether a referenced library/script tag is actually loaded anywhere before assuming it's live — `bill-extractor.js` referenced Tesseract but no page ever loaded it.

**The Quote document is one component, rendered identically in the admin builder and on the public share page — not two separate summaries.** `src/pages/quotes/QuoteDocument.tsx` is the full customer-facing document (branded header, hero pitch line, 6-metric grid, commercial summary, "what's included", AMC spotlight, payment schedule, install timeline, terms, WhatsApp/Call CTA, signature footer) — ported from the old repo's `quote-render.js`, whose own comment says exactly this ("the same QuoteView renders here as on the public page"). `QuoteBuilderPage` and `PublicQuotePage` both just build a `branding`/`amc` prop and pass it in; don't let them diverge into separate rendering again. Static marketing/legal copy that isn't backend data (segment pitch lines, the inclusions list, the install timeline) lives in `src/lib/quoteDocumentCopy.ts`, kept separate from `quoteCalculations.ts` which stays pure-numeric. `Entity.business_phone`/`business_email` (editable on the Business info tab, `BusinessInfoTab.tsx`), the public branding endpoint's footer/typography/GSTIN/address, and AMC plan details embedded in the public quote response (`PublicQuoteResponse.amc`) all now exist on the live backend — verified end-to-end (set contact info via Entity Settings, confirmed it round-trips through both the authenticated and public branding endpoints and renders identically, WhatsApp link included, on both `QuoteBuilderPage` and `PublicQuotePage`). `AMCPlanResponse.inclusion` (and therefore `PublicQuoteResponse.amc.inclusion`, which reuses it) is always an array, never `null` — the backend's `_to_amc_plan_response` helper normalizes `amc.inclusion or []` before serializing, even though the underlying DB column is nullable. Checked directly against a live plan created with an empty inclusion list (`GET .../amc-plans` returned `"inclusion": []`, not `null`) — don't add `?? []`-style null-guards for this field, the API contract already guarantees an array.

**`WorkOrderStatusResponse.project_status` is always populated, not just when the project actually advanced.** It reflects the parent project's status *after* the call either way — the backend only moves the project when the work order's `type`/`COMPLETED` transition matches the mapping table and the project is still at the exact fromstatus, and silently no-ops otherwise (no error). Don't word a UI message as "project moved to X" off this field alone unless you've confirmed a real transition happened (in practice: only surface it on `COMPLETED`, and phrase it as current state — "Project is now X" — not as a claimed move); this bit during Phase 9 verification (`ProjectDetailPage`/`WorkOrderDetailPage`'s transition handler). The same "reflects current state either way" rule applies to `CreateWorkOrderResponse.project_status` — creating a work order can *also* advance the project (e.g. `NEW` → `SITE_SURVEY_IN_PROGRESS`), so `ProjectWorkOrders`' create handler propagates it up via the `onProjectStatusChange` callback exactly the same way the skip-stage handler does — don't let one path update the parent's status and the other one leave it stale.

**Entity-admin vs field-role (`WORKER`/`TECHNICIAN`) is a route-tree split, mirroring the backend's `require_entity_admin_scope` gate.** `isEntityAdmin(roles)` (`src/lib/roles.ts`) is `ENTITY_ADMIN`/`ENTITY_SUPER_ADMIN` only — `RequireEntityAdmin` (`src/lib/RequireEntityAdmin.tsx`) wraps every back-office route (Leads/Quotes/Agreements/Projects/Entity Settings/Users/Dashboard) in `App.tsx`, and `AppLayout.tsx`'s nav links are conditioned on the same check, not on `user?.entity_id` alone. A non-admin entity user (`WORKER`/`TECHNICIAN`) lands on `/app/my-work-orders` (`MyWorkOrdersPage.tsx`, via `HomeRedirect.tsx`) instead of `/app/leads`, and only ever sees the work orders assigned to them (`GET .../work-orders/mine`) — never a leads/projects list, which the backend 403s them out of anyway. When adding a new back-office page, put it inside `<RequireEntityAdmin />` in `App.tsx`, not just behind `<ProtectedRoute />` — the guard, not just the missing nav link, is what stops a worker hitting the URL directly and getting a raw 403 instead of a redirect.

**Server-side pagination is `page`/`page_size`/`total` everywhere it exists** (Leads, Projects, and the entity-wide Quotes/Agreements lists) — the shared `src/lib/Pagination.tsx` component (prev/next, "X–Y of N", renders nothing when everything fits on one page) is the only pagination UI, don't build a page-specific one. A filter/search change resets to page 1 *in the same state update* as the filter change (see `handleStatusFilterChange` in `LeadsPage.tsx`/`ProjectsPage.tsx`), not in a separate `useEffect` keyed on the filter — the latter fires the list request twice (once for the stale page under the new filter, then again once the page-reset takes effect).

**A funnel/status filter that collapses several underlying values into one UI stage sends them all in one request, not one request per value.** `GET /entities/{entityId}/projects`'s `status` accepts repeated `?status=A&status=B` (see `PROJECT_PHASE_GROUPS` in `src/pages/projects/projectFunnel.tsx`, which maps a collapsed funnel stage like "Site survey" to its full `NEW`/`SITE_SURVEY_IN_PROGRESS`/`SITE_SURVEY_COMPLETED` status list) — `listProjects`'s `status` param already accepts `ProjectStatus | ProjectStatus[]`. Don't reintroduce a client-side merge-multiple-requests pattern for this; add the array form to the relevant `api/*.ts` function instead if a similar collapsed filter comes up elsewhere.

**Quotes/Agreements pages show exactly one entity plus a forward-looking action, never a merged "leads without a quote yet" row.** `QuotesPage`/`AgreementsPage` list quotes/agreements only (`listEntityQuotes`/`listEntityAgreements`, real server pagination); "generate" lives one step upstream instead — a `NEW` lead's row on `LeadsPage` gets a "Generate quote" button, a `QUOTE_ACCEPTED` lead's row on `QuotesPage` gets "Generate agreement", derived from `lead_status` embedded on each quote/agreement row (no second query). Don't reintroduce the old pattern of fetching every lead and fetching each one's quote in a loop — the backend join-based list endpoints exist specifically to replace that N+1.

**Login accepts an email or a phone number in one field.** `LoginPage.tsx`'s single `identifier` input (`type="text"`, not `type="email"` — it may hold a phone number) and `login(identifier, password)` (`src/api/auth.ts`) send `{"identifier": ..., "password": ...}`; the backend routes by whether the value contains `@`. Don't reintroduce a dedicated email field or `type="email"` validation here.

**Mobile card layout: an action-only cell (no label, just buttons) needs its own class, not the generic `td`.** The mobile breakpoint turns every `<td>` into a `display: flex; justify-content: space-between` label/value row via `content: attr(data-label)` — a cell with only a button and no `data-label` overflows or mis-lays-out under that rule. The fix is a dedicated `*-table-action-cell` class per page (`leads-table-action-cell`, `quotes-table-action-cell`, `projects-table-action-cell`) with a **compound selector** override (`.leads-table td.leads-table-action-cell`, not just `.leads-table-action-cell` — a bare class doesn't outrank `.leads-table td`'s specificity) that switches to `display: flex; flex-direction: column` on mobile. `flex-direction: column` specifically, not `display: block` — `.projects-btn`/`.quotes-btn`/`.leads-btn` are `display: inline-block`, so two full-width buttons in a `block` cell sit side by side and overflow instead of wrapping; `flex-column` forces each onto its own row (see `WorkOrderDocuments.tsx`'s View/Delete cell, which is what surfaced this). Copy an existing `*-table-action-cell` pair (desktop right-aligned flex row + mobile column override) rather than inventing new layout rules per page.

**Every shared button class (`.projects-btn`, `.quotes-btn`, `.leads-btn`, `.entity-btn`) needs its own `:hover:not(:disabled)` rule** — none of them inherit one from anywhere, and it's easy to add a new page's buttons off one of these classes without noticing hover does nothing. The pattern: base variant hovers to `var(--app-bg)` background / `var(--app-text-muted)` border, `.primary` hovers to `var(--app-accent-hover)`, `.danger` (where it exists) hovers to `var(--app-danger-bg)`. `.entities-action-btn` (`EntitiesPage.css`) already had this from earlier work — copy its shape when adding a new button class rather than reinventing it.

**Work order documents are optional and independent of `WorkOrderStatus`.** `WorkOrderDocuments.tsx` (mounted at the bottom of `WorkOrderDetailPage.tsx`, visible regardless of `NEW`/`IN_PROGRESS`/`COMPLETED`) — upload does a client-side size pre-check against `MAX_WORK_ORDER_DOCUMENT_SIZE_BYTES` before ever hitting the network (the backend enforces the real limit; this is just to avoid an obviously-doomed upload), View opens a fresh presigned URL per click (they expire, so don't cache one), and the "X/5" counter against `MAX_WORK_ORDER_DOCUMENTS` disables the file input once at the cap. Access to the whole feature (upload/list/view/delete) is whatever the page itself already required (entity admin or the work order's current assignee) — the component doesn't re-check permissions itself, same reasoning as the assign section below it. `ACCEPTED_EXTENSIONS` in that file (`.pdf,.jpg,.jpeg,.png,.webp,.xls,.xlsx`) must stay in sync with the backend's `ALLOWED_DOCUMENT_TYPES` — it was extended once already (Excel), keep both sides matched if it changes again.

**A work order can exist before a Project does.** `WorkOrder.project_id` is nullable — `POST/GET /entities/{entityId}/leads/{leadId}/work-orders` (`createLeadWorkOrder`/`listLeadWorkOrders` in `src/api/workOrders.ts`) creates/lists work orders directly against a `Lead`, for an early site survey ahead of quoting/agreement. `LeadWorkOrders.tsx`, mounted at the bottom of `LeadDetailPage.tsx`, is the only UI for this — a "+ Create site survey" button (disabled while a non-`COMPLETED` `SITE_SURVEY` already exists for the lead, mirroring the backend's `ensure_work_order_type_not_already_open`) plus a list linking to the normal `/app/work-orders/:id` detail page. Deliberately out of scope: no new `Lead.status` values, no "skip" option, and no linking the lead-level work order to a project created later — it just stays a standalone row. Every `WorkOrderListItem`/`WorkOrderDetailResponse` now embeds a `lead: LeadSummary` (name/mobile/email/address/status) so any list or detail view can show the customer's contact and address without a second lookup (see the Customer/Address columns on `ProjectWorkOrders.tsx` and the Customer/Address rows on `WorkOrderDetailPage.tsx`) — `WorkOrderDetailPage`'s back-link target/label also branches on `project_id` being null (`← Back to lead` → `/app/leads/{lead_id}`, not `← Back to project` → `/app/projects`).

**Reassign is disabled when the selected assignee hasn't actually changed**, not just when the select is empty — `WorkOrderDetailPage.tsx`'s Assign/Reassign button compares `assigneeType`+the selected id against `wo.assignee` and disables if they match, so re-clicking "Reassign" with the same person selected is a no-op instead of a wasted API call.

## Verification convention

There's no automated test suite. Every feature in this repo has been verified by: `npx tsc -b` for typecheck, then driving the actual UI in a browser against the real local backend (`../solaros-online-backend`, must be running — see this repo's README), and cross-checking persistence with direct `curl` calls to the backend API. When the browser-automation pane gets visually stuck (a recurring flakiness in this environment, not an app bug), prefer DOM inspection via `javascript_tool`/`read_page` over trusting a screenshot — confirmed multiple times that a frozen-looking screenshot doesn't mean the app is actually broken.

**`npx tsc --noEmit` (no `-b`) from the repo root silently checks nothing and exits clean regardless of real errors.** The root `tsconfig.json` is solution-style (`"files": []`, just `references` to `tsconfig.app.json`/`tsconfig.node.json`) — without `-b`, plain `tsc` has no files to check and reports success. This bit once: a genuine type error in `AmcActionTable.tsx` (an `Assignee` object literal missing the `email`/`phone` fields the type requires) passed `tsc --noEmit` clean but broke `npm run build` (`tsc -b && vite build`). Always use `npx tsc -b` (matches this file's own guidance above) or `npm run build` to actually verify — never bare `tsc --noEmit`.

Test data accumulates in the local Postgres DB across sessions (leads named "Test X", extra AMC plans, etc.) — that's expected and fine for a dev DB; don't feel obligated to clean it up unless it's actively confusing a specific test.

## Environment & config

`.env.development` sets `VITE_API_BASE_URL` (defaults to `http://127.0.0.1:8000/api/v1`). The dev server is **pinned to port 3000** in `vite.config.ts` (`server.port` + `strictPort`) because the backend's local `CORS_ORIGINS` only allows `http://localhost:3000` — don't change one without the other. See the README for the full local-dev walkthrough (pulling activation tokens from Postgres when `RESEND_API_KEY` isn't set, approving a test entity via the seeded system admin, etc.).

## Safety notes for agents

- `git status` before any command that could discard uncommitted work, per the standing repo-wide instruction.
- This repo's established practice has been to commit after each verified, working change with a descriptive message (see `git log` for the pattern/detail level expected) — but only when the user has actually asked for the feature; don't build ahead of what's been requested.
- Never fabricate verification — if the backend isn't running or a check can't actually be performed, say so rather than claiming something works.
